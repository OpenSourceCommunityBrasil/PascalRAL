# ral-build reference: why the recipe is what it is

## The seven msbuild traps, in the order they bite

1. **`/p:UsePackages=true` is mandatory.** `CodeGear.Delphi.Targets` emits `-LU` only
   when `UsePackages` or `DCC_EnabledPackages` is true, and no `.dproj` here sets
   either. Without it `msbuild` links Indy or FireDAC **statically**: the package
   compiles clean and the IDE refuses it with a duplicate-unit error. `IndyRAL.bpl`
   comes out at 1.5 MB instead of 60 KB.
2. **Filter `DCC_UsePackage` against the `.dcp` that exist.** With `-LU` on, a name
   with no `.dcp` is a hard `E2202 Required package 'X' not found`.
3. **The `Base` group's `DCC_UnitSearchPath` is not applied this way.** It matters for
   `SynopseRAL` (mORMot2 is external) and `RALCompressBrotliPackage` (`brotli_libc` and
   `libbrotli.obj` are found by search path): pass them yourself (see SKILL.md).
   `mormot2` is an **IDE** environment variable that `msbuild` does not see: pass
   `/p:mormot2=...`.
4. **Set `BDS` and `BDSCOMMONDIR`** when the shell was not initialized by
   `rsvars.bat`. Without `BDS` the `.dproj` never imports the Delphi targets and
   `msbuild` answers `MSB4057: the "Build" target does not exist in the project`,
   which reads like a broken package and is not. `rsvars.bat` does not set `BDSLIB`.
5. **A `;` inside a `/p:` value is a property separator**: `/p:A=x;y` dies with
   `MSB1006 invalid property`. Escape each one as `%3B` (`%%3B` inside a `.bat`).
6. **`DCC_CBuilderOutput` is `All` in the `Base` group, and only Debug/Win32 turns it
   off.** A Release build then emits C++ headers, which reject mORMot's old-style
   `object` types: `E1025 Unsupported language feature: 'Object'` at line 1 of
   `mormot.lib.openssl11.pas`. Pass `/p:DCC_CBuilderOutput=None`; no package here is
   consumed from C++Builder.
7. **When a unit is "not found", add the package that owns it to `DCC_UsePackage` -
   never this repository's `src` to `DCC_UnitSearchPath`.** With `src` on the path the
   package builds and silently compiles the other package's unit into its own `.bpl`;
   the IDE then refuses it with `Cannot load package 'A'. It contains unit 'X', which
   is also contained in package 'B'`, and answering **No** moves it to
   `Disabled Packages`. `bplunits` reports exactly this case ("RAL unit of another
   package").

## Calling dcc32 directly

`dcc32`/`dcc64` with `--no-config` ignores the `.dproj`, so `DCC_UsePackage` has to be
replicated as `-LU`, or Indy and FireDAC are linked in statically:

```bat
dcc32 --no-config -B -Q -NS"System;System.Win;Winapi;Vcl;Data;Data.Win;Xml;Web;Soap;Datasnap" ^
  -U"<BDS>\lib\win32\release;<BDSCOMMONDIR>\Dcp" -I"<repo>\src\core;<repo>\src\languages" ^
  -LU"rtl;IndySystem;IndyProtocols;IndyCore;PascalRAL" ^
  -LE"<out>" -LN"<out>" pkg\Delphi\Engine\IndyRAL.dpk
```

A `.dpk` from a clean checkout stops at `E1026 File not found: 'PascalRAL.res'`: the
`.res` files are generated by the IDE (or by `msbuild`) and are not tracked. Build
once with `msbuild`, or check the units with a throwaway program (`ral-check-unit`).

Pass every path in Windows form (`C:\temp\x`). Git Bash rewrites `/c/...` and `/tmp/...`
arguments into something like `C:C:/Program Files/Git/...`, and the compiler dies with
`F2039 Could not create output file`.

## Platforms

Shared code has to compile for every platform the packages claim, not only Win32/Win64.
A unit compile needs no SDK and no linker: `dccaarm`, `dccaarm64` or `dcclinux64` over a
throwaway unit (`ral-check-unit`). What does not compile today, by design or because of
a third party: Synopse on Delphi Android/iOS (mORMot2 has no Delphi mobile target),
Zeos, brotli and zstd off Windows on Delphi, `RALDBFireDAC` on mobile.
